# 搜索与发现 — 基于当前项目的迭代开发文档

> 优先级：P0 | 涉及模块：`items` + `interactions` + `system_config` + `frontend/uni-app` | 当前状态：基础能力已落地，下一步应做后端增强

---

## 1. 当前项目现状

搜索与发现并不是纯未来能力，当前已经完成了第一版：

### 已落地后端

- `GET /api/v1/items/`
  - 支持 `q`
  - 支持 `category`
  - 支持 `season`
  - 支持 `region_code`
  - 支持 `publisher_id`
  - 支持 `current_season_only`
- 搜索字段已覆盖：
  - `title`
  - `description`
  - `province`
  - `city`
  - `flavor_tags__tag_name`

### 已落地前端

- 首页支持搜索名称、地点、风味标签
- 今日上新页支持搜索
- 社区页支持搜索动态内容、商品名称、地点、标签

### 当前不足

- 没有热门搜索
- 没有搜索历史回传
- 排序能力仍然单一，主要是 `created_at desc`
- 筛选维度还没有全部下沉到后端
- 没有独立搜索接口，搜索能力与列表接口耦合
- 热门搜索和搜索日志还未接入异步处理

所以这份文档应该从“重做搜索”改成“把现有搜索升级成真正的发现系统”。

---

## 2. 当前接口基线

当前主接口：

`GET /api/v1/items/`

当前参数：

| 参数 | 说明 |
|------|------|
| `skip` | 偏移量 |
| `limit` | 数量 |
| `q` | 关键词 |
| `category` | 分类 |
| `season` | 季节 |
| `region_code` | 地区编码 |
| `publisher_id` | 发布者 |
| `current_season_only` | 只看当前季节 |

这意味着第二阶段不一定要新开一个搜索接口，也可以先把 `/items/` 扩成标准搜索接口。

---

## 3. 第二阶段目标

目标不是“能搜到”，而是“更快找到想交换的东西”。

下一阶段建议补齐 4 件事：

1. 后端多维筛选完善
2. 排序能力完善
3. 热门搜索与搜索历史
4. 搜索结果页与推荐结果联动

---

## 4. 数据字段与筛选设计

当前 `Item` 已具备：

- `category`
- `season`
- `shelf_life`
- `portability`
- `province`
- `city`
- `region_code`
- `flavor_tags`

因此筛选设计应直接建立在这些字段上，而不是新增一套与现有模型冲突的字段。

### 建议新增的查询参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `shelf_life` | string | 对应 `SystemOption(ShelfLife)` |
| `portability` | string | 对应 `SystemOption(Portability)` |
| `tag` | string | 单标签搜索 |
| `sort` | string | `fresh / hot / match` |

### 查询逻辑建议

- `q`：模糊搜索名称、描述、地区、标签
- `category`：精确过滤
- `season`：精确过滤
- `shelf_life`：精确过滤
- `portability`：精确过滤
- `tag`：精确或半模糊匹配 `FlavorTag.tag_name`

## 5. 排序设计

### 5.1 `fresh`

当前默认排序，按 `created_at desc`

### 5.2 `hot`

当前项目没有显式的浏览量字段，因此第一版热门排序建议采用轻量代理指标：

```text
热度分 = 交换请求数 + 风味投票数 + 社区帖子数
```

可从这些表聚合：

- `exchange.ExchangeRequest`
- `interactions.FlavorTag`
- `community.CommunityPost`

### 5.3 `match`

登录用户可走智能推荐逻辑，未登录用户降级为 `fresh`

也就是说搜索和推荐不是两套完全独立系统，而是：

- 搜索负责召回候选集
- 推荐负责排序

---

## 6. 热门搜索设计

### 6.1 为什么值得做

当前首页和社区页已经有搜索框，但没有给用户“搜什么”的引导。

热门搜索可以解决：

- 冷启动用户不知道搜什么
- 热门特产、热门地区自然曝光

### 6.2 第一版实现建议

当前项目已经接入 `Celery`，但热门搜索第一版仍建议保持轻量：

- 搜索时同步写 Redis ZSet
- 同时按需落库 `SearchLog`
- 当搜索量明显上升后，再把日志写入和热词聚合迁移到 Celery 异步任务

建议新增模型：

```python
class SearchLog(models.Model):
    keyword = models.CharField(max_length=128)
    user = models.ForeignKey(LocalUser, null=True, blank=True, on_delete=models.SET_NULL)
    scene = models.CharField(max_length=32, default="items")
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        indexes = [
            models.Index(fields=["keyword", "created_at"]),
            models.Index(fields=["scene", "created_at"]),
        ]
```

### 6.3 接口建议

- `GET /api/v1/items/search/hot`
- `POST /api/v1/items/search/log`

如果不想新增写接口，也可以在查询接口中同步记录。

## 9. 前端配套建议

当前首页与今日上新页已经有较完整的搜索 UI，因此前端工作重点不是“重新造页面”，而是：

- 对齐新的后端筛选参数
- 新增排序选择
- 接热门搜索词
- 新增空态推荐

建议顺序：

1. 首页先接入排序与更多筛选
2. 今日上新保持轻量
3. 社区页继续维持“关键词搜索”为主

---

## 10. 与当前项目的关系结论

搜索与发现不是从零开始做，而是应该明确为：

`已完成基础搜索 -> 下一步做筛选、排序、热搜、推荐融合`

文档必须基于当前真实结构：

- 模型是 `Item`
- 标签在 `interactions.FlavorTag`
- 选项在 `system_config.SystemOption`
- 缓存用 `core.cache_utils`

而不是继续引用旧的 `catalog/Product` 设计。
