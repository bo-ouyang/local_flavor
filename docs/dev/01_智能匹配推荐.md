# 智能匹配推荐 — 基于当前项目的后续开发文档

> 优先级：P0 | 涉及模块：`items` + `exchange` + `interactions` + `users` + `core` | 当前状态：未落地，建议作为下一阶段重点

---

## 1. 当前项目现状

当前首页推荐流本质上还是“最新发布流”，已具备这些基础能力：

- `items` 已支持按 `q / category / season / region_code / publisher_id` 过滤。
- `interactions` 已有风味标签与用户投票数据，可作为偏好信号。
- `exchange` 已有交换请求与 `completed` 状态，可作为“交换成功样本”。
- `users` 已有用户省市、`region_code`、经纬度信息，可用于地域偏好。
- `core.cache_utils` 已具备缓存版本号和 Redis/LocMem 缓存机制。

当前还不具备的内容：

- 用户偏好快照
- 推荐日志与效果追踪
- 独立推荐接口
- 推荐结果缓存失效策略

当前已经具备的新基础设施：

- Django 已接入 `Celery` 基础设施
- 后续推荐偏好重算、推荐日志回流、缓存失效可以逐步迁移到异步任务

这意味着推荐能力不需要从零开始，但文档必须严格贴合当前项目结构，不能再沿用旧的 `catalog / accounts / Product` 命名。

---

## 2. 目标

为首页“交换推荐流”提供个性化排序，让用户更快看到自己更可能发起交换、也更可能完成交换的特产。

第一阶段不做复杂模型，采用：

`规则打分 + 用户偏好快照 + Redis 缓存`

这样可以在不引入 Elasticsearch 的前提下，先把推荐能力跑起来。即便当前已经接入 `Celery`，第一版仍建议优先保证推荐逻辑可同步运行，再视性能决定是否迁移到异步。

---

## 3. 推荐分层策略

### 3.1 冷启动用户

适用于：

- 没有风味投票记录
- 没有完成交换记录

推荐规则：

- 当前季节优先
- 新鲜度优先
- 与用户同省/同城市优先
- 热门特产适度抬权

### 3.2 轻度活跃用户

适用于：

- 有风味投票
- 有浏览和搜索行为
- 但完成交换次数还不多

推荐规则：

- 结合投票标签和已发布商品类别
- 兼顾同地区与跨地区探索

### 3.3 已完成交换用户

适用于：

- 已有 `completed exchange`

推荐规则：

- 基于已完成交换的特产类别、标签、地区偏好做排序
- 降低对已交换过同类特产的重复曝光

---

## 4. 打分设计

建议第一版采用以下权重：

```text
总分 = 风味偏好(35%) + 类别偏好(20%) + 季节匹配(15%) + 地区相关性(10%) + 交换完成率(10%) + 新鲜度(10%)
```

### 4.1 风味偏好

数据来源：

- 用户历史风味投票：`interactions.FlavorVote`
- 已完成交换关联特产的风味标签：`interactions.FlavorTag`

思路：

- 先生成用户风味偏好向量
- 再根据 `Item.flavor_tags` 计算匹配度

### 4.2 类别偏好

数据来源：

- 用户已发布的特产类别
- 用户已完成交换涉及的特产类别

### 4.3 季节匹配

当前项目里 `Item.season` 已是枚举值，可以直接和 `core.time_utils.get_current_season()` 对比。

### 4.4 地区相关性

当前用户已有：

- `province`
- `city`
- `region_code`
- `latitude`
- `longitude`

第一版先用 `province / city / region_code` 做离散匹配，不做地理距离计算。

### 4.5 交换完成率

不是“信用分”，而是从 `exchange_requests` 里估算该特产对应的交换活跃度与完成度。

说明：

- 当前项目没有独立信用体系
- 文档中不应再引用不存在的 `credit_score`

### 4.6 新鲜度

沿用当前 `created_at` 计算逻辑即可，7 天内满分，之后线性衰减。

## 5. 数据模型建议

### 5.1 用户偏好快照（新增）

建议新增到 `users` 或 `items` 侧，推荐放在 `users` 中更合理。

```python
class UserPreferenceSnapshot(models.Model):
    user = models.OneToOneField(LocalUser, on_delete=models.CASCADE, related_name="preference_snapshot")
    flavor_vector = models.JSONField(default=list)
    category_weights = models.JSONField(default=dict)
    region_weights = models.JSONField(default=dict)
    exchange_completed_count = models.PositiveIntegerField(default=0)
    updated_at = models.DateTimeField(auto_now=True)
```

### 5.2 推荐曝光日志（新增）

```python
class ItemRecommendLog(models.Model):
    user = models.ForeignKey(LocalUser, on_delete=models.CASCADE, related_name="recommend_logs")
    item = models.ForeignKey(Item, on_delete=models.CASCADE, related_name="recommend_logs")
    score = models.FloatField()
    scene = models.CharField(max_length=32, default="home")
    shown_at = models.DateTimeField(auto_now_add=True)
    clicked = models.BooleanField(default=False)
    exchanged = models.BooleanField(default=False)

    class Meta:
        indexes = [
            models.Index(fields=["user", "shown_at"]),
            models.Index(fields=["item", "shown_at"]),
        ]
```

说明：

- 第一版可以先不记录点击/交换回流，只记录曝光
- 如果赶工期，推荐日志可以延后到第二阶段

## 6. 核心实现建议

### 6.1 推荐接口

新增接口：

`GET /api/v1/items/recommended`

建议参数风格与现有 `/items/` 保持一致：

| 参数 | 类型 | 说明 |
|------|------|------|
| `skip` | int | 偏移量 |
| `limit` | int | 数量，默认 10，最大 50 |
| `category` | string | 可选分类过滤 |
| `q` | string | 可选关键词过滤 |

返回结构延续当前统一响应封装：

```json
{
  "code": 0,
  "message": "ok",
  "data": [
    {
      "id": 12,
      "title": "云南松茸",
      "category": "Dish",
      "province": "Yunnan",
      "city": "Diqing",
      "images": ["https://..."],
      "score": 0.84,
      "reason_tags": ["偏好鲜香", "当季推荐", "交换完成率高"]
    }
  ]
}
```

### 6.2 推荐原因说明

第一版强烈建议返回 `reason_tags`，否则用户无法理解为什么推荐给自己。

可选原因：

- 偏好麻辣
- 当季推荐
- 同城优先
- 最近很受欢迎
- 交换完成率高

### 6.3 缓存策略

沿用当前 `core.cache_utils`：

- key：`items:recommended:{user_id}`
- TTL：10 分钟
- 用户偏好变化时主动失效

触发失效场景：

- 新增风味投票
- 完成交换
- 用户地区更新

## 7. 偏好更新策略

### 第一版建议

第一版仍建议优先同步更新：

- 用户完成交换后，同步刷新 `UserPreferenceSnapshot`
- 用户投票后，同步刷新 `UserPreferenceSnapshot`

### 第二版再考虑

- Celery 异步刷新
- 定时离线重算偏好
- Redis Sorted Set 预计算推荐

说明：

- 当前项目已具备 Celery 基础设施，但推荐一期不应一开始就强依赖异步链路
- 文档必须基于当前工程现实，不应默认依赖异步任务系统

---

## 8. 首页接入方案

当前首页前端在 `frontend/uni-app/src/pages/index/index.vue`，现在直接请求 `/items/`。

建议改造为：

1. 登录用户优先请求 `/items/recommended`
2. 游客继续走 `/items/`
3. 推荐接口失败时兜底为 `/items/`

这样上线风险最低。

## 10. 当前文档结论

这项能力依然值得做，而且是最接近“产品差异化”的功能之一；但实现方式必须从当前项目出发：

- 使用 `items / users / exchange / interactions`
- 不再引用不存在的 `catalog / accounts / Product / credit_score`
- 第一版不默认依赖 Celery
- 先做可解释推荐，而不是黑盒推荐
