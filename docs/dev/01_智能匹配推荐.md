# 智能匹配推荐 — 当前实现与后续开发文档

> 优先级：P0 | 涉及模块：`items` + `exchange` + `interactions` + `users` + `core` | 当前状态：Phase 1 已落地，Phase 2 效果追踪待实施

---

## 1. 当前项目现状

当前首页已接入可解释的个性化推荐流，Phase 1 已具备这些能力：

- `users.UserPreferenceSnapshot` 保存风味、类别、地区和已完成交换偏好数据。
- `items.recommendation` 使用风味、类别、季节、地区、发布者交换经验和新鲜度进行规则打分。
- `GET /items/recommended` 对最近 200 个已审核且可见的候选评分，并支持 `q / category / skip / limit`。
- 推荐评分批量聚合候选发布者的已完成交换数量，候选数量增加时仍固定执行两条聚合 SQL。
- 登录用户首页优先请求推荐接口，失败时回退普通列表；游客直接使用普通列表。
- 接口返回最多 3 个去重的 `reason_tags`，首页特产卡片已展示推荐理由。
- 推荐结果按用户、查询参数和 `items` 缓存命名空间版本缓存。

Phase 2/3 尚未具备、需要继续实施的内容：

- 推荐曝光、点击、发起交换等行为日志与效果指标
- 根据真实转化结果校准规则权重
- 用户偏好、交换完成和地区变化后的推荐缓存精准失效
- 定时离线重算、预计算推荐和详情页等多场景推荐

当前已经具备的新基础设施：

- Django 已接入 `Celery`，风味投票、交换完成和地区更新后会异步重算用户偏好快照
- 后续推荐日志回流、周期性离线重算和预计算可以继续使用异步任务

这意味着推荐能力不需要从零开始，但文档必须严格贴合当前项目结构，不能再沿用旧的 `catalog / accounts / Product` 命名。

## 2. 目标

Phase 1 已为首页“交换推荐流”提供个性化排序，让用户更快看到自己更可能发起交换的特产。

当前实现采用：

`规则打分 + 用户偏好快照 + Django 缓存（默认 LocMem，可配置 Redis）`

推荐请求中的规则打分同步执行，偏好快照通过 Celery 异步重算。Phase 2 的目标是在不引入复杂模型的前提下补齐曝光、点击和交换转化数据，用真实效果校准当前规则。

---

## 3. 推荐分层策略

### 3.1 冷启动用户

适用于：

- 没有风味投票记录
- 没有完成交换记录

推荐规则：

- 当前季节优先
- 新鲜度优先
- 与用户 `region_code` 相同的特产优先

### 3.2 轻度活跃用户

适用于：

- 有风味投票
- 有已发布特产形成的类别偏好
- 但完成交换次数还不多

推荐规则：

- 结合投票标签和已发布特产类别
- 兼顾当前地区与历史偏好地区

### 3.3 已完成交换用户

适用于：

- 已有 `completed exchange`

推荐规则：

- 基于已完成交换的特产类别、标签、地区偏好做排序
- 使用候选发布者已完成交换数量补充交换经验分

当前尚未实现已交换同类去重或降低重复曝光，属于 Phase 2 后续优化。

## 4. 打分设计

当前规则采用以下权重上限：

```text
总分 = 风味偏好(35%) + 类别偏好(20%) + 季节匹配(15%) + 地区相关性(10%) + 交换经验(10%) + 新鲜度(10%)
```

### 4.1 风味偏好

数据来源：

- 用户历史风味投票：`interactions.FlavorVote`
- 已完成交换关联特产的风味标签：`interactions.FlavorTag`

思路：

- 先生成用户风味偏好向量
- 再根据 `Item.flavor_tags` 计算匹配度

### 4.2 类别偏好

数据来源：

- 用户已发布的特产类别
- 用户已完成交换涉及的特产类别

### 4.3 季节匹配

当前项目里 `Item.season` 已是枚举值，可以直接和 `core.time_utils.get_current_season()` 对比。

### 4.4 地区相关性

当前用户已有：

- `province`
- `city`
- `region_code`
- `latitude`
- `longitude`

当前使用 `region_code` 精确匹配；若候选地区出现在用户历史地区权重中，则给予较低的历史地区分。不做省市模糊匹配或地理距离计算。

### 4.5 交换经验

不是“完成率”或“信用分”。当前实现统计候选特产发布者作为请求方或拥有者参与的已完成交换数量；每次已完成交换增加 0.02，最高贡献 0.10。参与超过 5 次已完成交换时返回“交换经验丰富”推荐理由。

说明：

- 该指标没有使用总请求数作为分母，不能解释为交换完成率
- 批量评分前统一聚合候选发布者的完成数量，发布者数量增加时仍固定执行两条聚合 SQL
- 当前项目没有独立信用体系
- 文档中不应再引用不存在的 `credit_score`

### 4.6 新鲜度

当前沿用 `created_at` 计算：7 天内贡献 0.10，8 至 30 天贡献 0.05，超过 30 天不贡献新鲜度分。

## 6. 核心实现

### 6.1 推荐接口（Phase 1 已实现）

当前接口：

`GET /api/v1/items/recommended`

参数风格与现有 `/items/` 保持一致：

| 参数 | 类型 | 说明 |
|------|------|------|
| `skip` | int | 偏移量 |
| `limit` | int | 数量，默认 10，最大 50 |
| `category` | string | 可选分类过滤 |
| `q` | string | 可选关键词过滤 |

返回结构延续当前统一响应封装：

```json
{
  "code": 0,
  "message": "ok",
  "data": [
    {
      "id": 12,
      "title": "云南松茸",
      "category": "Dish",
      "province": "Yunnan",
      "city": "Diqing",
      "images": ["https://..."],
      "score": 0.84,
      "reason_tags": ["偏好鲜香", "当季推荐", "交换经验丰富"]
    }
  ]
}
```

### 6.2 推荐原因说明

当前接口返回最多 3 个去重的 `reason_tags`，首页会直接展示。

当前可能返回的原因：

- 偏好{风味标签}
- 当季推荐
- 同城优先
- 常换地区
- 交换经验丰富
- 新鲜发布

### 6.3 缓存策略

当前沿用 `core.cache_utils`：

- key 包含用户 ID、`items` 命名空间版本和规范化查询参数摘要
- TTL 使用 `CACHE_TTL_ITEMS_LIST`，默认 60 秒
- 特产或风味标签变化时提升 `items` 命名空间版本，使旧推荐缓存自然失效

Phase 2 待补充的精准失效场景：

- 异步偏好快照重算完成后，失效对应用户的推荐缓存
- 完成交换后，及时反映双方新的偏好与发布者交换经验
- 用户地区更新后，及时反映新的地区匹配结果

## 7. 偏好更新策略

### 当前策略

- 用户完成交换后，通过 Celery 异步刷新双方的 `UserPreferenceSnapshot`
- 用户投票后，通过 Celery 异步刷新当前用户的 `UserPreferenceSnapshot`
- 用户地区更新后，通过 Celery 异步刷新当前用户的 `UserPreferenceSnapshot`

### 后续增强

- 定时离线重算偏好
- Redis Sorted Set 预计算推荐
- 异步任务失败重试与可观测性
- 偏好更新后的推荐缓存精准失效

说明：

- 在线推荐打分仍是同步路径，不依赖离线预计算结果
- 偏好刷新依赖 Celery，部署环境需要保证 worker 正常运行

## 10. 当前文档结论

推荐 Phase 1 已完成，下一步重点是建立效果追踪闭环，而不是立即引入复杂模型：

- 使用 `ItemRecommendLog` 或等效事件模型记录曝光、点击和交换转化
- 用实际转化数据评估并校准现有规则权重
- 补齐偏好变化后的缓存精准失效和异步任务可观测性
- 保持可解释推荐，再根据数据量和效果决定是否引入更复杂模型
