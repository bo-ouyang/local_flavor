# ADR-0001：采用可撤销的服务端 opaque 认证会话

- 状态：已接受
- 日期：2026-07-31
- 范围：AUTH-01A 后端认证与兼容层

## 背景

项目用户实体是业务模型 `users.LocalUser`，并非 Django 的 `AUTH_USER_MODEL`。旧认证使用 `TimestampSigner` 将 `openid` 直接签入 Bearer Token，只有统一过期时间，没有服务端会话记录，因此无法做到单设备登出、主动撤销、刷新轮换或重放检测。REST 视图和 WebSocket 又分别解析 Token，DRF 的 `request.user` 与用户限流无法识别真实业务用户。

本阶段必须同时满足：短期访问凭据、长期刷新凭据、即时撤销、设备会话列表、REST/WS 同义、旧客户端灰度迁移，以及数据库和日志中不保存明文凭据。

## 备选方案

### 方案 A：SimpleJWT + blacklist

优点：生态成熟，提供 access/refresh、refresh rotation 与 blacklist app；JWT 验签可在不查会话表的情况下完成。

代价与风险：

- SimpleJWT 默认围绕 Django 用户认证模型和用户标识字段工作，而当前 `LocalUser` 不是 `AUTH_USER_MODEL`。直接接入需要身份模型适配，或先迁移用户模型；两者都会扩大 AUTH-01 的数据库、后台和权限迁移范围。
- 要满足“撤销后 REST/WS 立即失败”，仍需在请求时查询 blacklist/会话状态，削弱无状态 JWT 的主要收益。
- JWT payload 会复制用户标识和时效信息，令牌泄露后的应急控制仍依赖额外状态表。
- 当前规模没有跨服务离线验签需求，引入 JWT 声明、签名算法和密钥轮换并不能带来足够收益。

### 方案 B：高熵 opaque 凭据 + 服务端会话

优点：凭据本身不承载用户数据；每次解析都读取唯一摘要对应的会话，因此撤销、刷新轮换和设备管理语义直接且一致；可以继续使用现有 `LocalUser`，不扩大身份模型迁移范围。

代价：每个认证请求增加一次按唯一摘要索引的数据库查询；服务端会话表需要清理过期记录。当前业务规模下这是可接受的，并且后续可以用短时缓存优化，但缓存必须保证撤销语义。

## 决策

选择方案 B。使用 Python `secrets.token_urlsafe(32)` 生成约 256 bit 随机访问/刷新凭据，分别加 `lf_a_` 和 `lf_r_` 前缀。数据库只保存完整 Token 的 SHA-256 摘要，摘要字段具有唯一约束；明文只在签发或轮换响应中返回一次。

默认访问有效期 15 分钟，会话家族绝对有效期 30 天，均由环境变量配置且刷新不会延长家族绝对期限。refresh 摘要由 `AuthRefreshToken` 保留为历史链，记录 `used_at` 与 successor。刷新在 `transaction.atomic()` 中用 `select_for_update()` 锁定 refresh 与会话，正常轮换原子标记旧凭据已使用并创建 successor；已使用 refresh 再出现会被识别为重放，并在返回 401 前提交整个会话家族撤销。这覆盖“被盗 Token 先刷新、合法客户端随后使用旧 Token”的场景。

登出与用户撤销通过 `revoked_at` 立即影响 REST 和 WebSocket 的共享解析器。WebSocket scope 保存认证会话身份，consumer 在每个入站事件与每次 group push 投递前重新解析；握手后发生撤销或 access 过期时以 4401 关闭，避免长连接绕过服务端状态。

DRF 使用自定义 `BaseAuthentication`，成功时返回 `(LocalUser, AuthSession)`，使 `request.user`、`request.auth` 和 `UserRateThrottle` 获得真实身份。`LocalUser.is_authenticated` 固定为 `True`；这只表达该实例已通过本认证器验证，不赋予 Django admin 权限。

## 威胁模型与边界

- 数据库泄露：攻击者只能获得 SHA-256 摘要，无法直接用摘要作为 Bearer Token。凭据具有足够熵，离线穷举不可行。
- 传输或客户端存储泄露：Bearer Token 仍可在有效期内被重放，因此生产环境必须使用 TLS；access 保持短期，用户可撤销对应会话。
- refresh 重放：成功刷新会保留已使用摘要并创建 successor。同一旧 refresh 的串行或 PostgreSQL 并发重放会撤销整个家族，因此攻击者先拿到的 successor 也立即失效。
- 伪造/过期/撤销：解析器统一拒绝；客户端提交的用户 ID 或会话所有者 ID不参与身份判定。
- 日志：应用不得记录 Authorization、query Token、refresh Token 或摘要。应用请求日志只使用 `request.path`；部署文档的 Nginx access log 只记录不含参数的 `$uri`。迁移期 `/ws/` 还必须用官方支持的 location 级 `error_log /dev/null emerg;` 临时抑制可能包含原始 request/query 的 upstream timeout/connect failure 等错误日志；前置 CDN/LB 同样不得记录完整 URL。AUTH-01B 关闭 query 后立即删除该抑制，恢复正常诊断与 OPS 告警。
- SHA-256 在这里不是密码哈希：输入是服务端生成的高熵随机数，不需要慢哈希；唯一索引需要确定性摘要。

## 兼容与迁移

1. AUTH-01A 登录顶层 `access_token`（以及兼容 `token`）继续返回旧 `TimestampSigner` 凭据，因为现有前端实际读取顶层 `access_token`。签发与 resolver 共用 `legacy_tokens_allowed(now)` 运行时判定，截止后即使进程未重启也不再返回 legacy 字段。新 opaque 凭据只位于明确的 `session: {access_token, refresh_token, expires_in, access_expires_at, refresh_expires_at, session_id}` 对象，顶层不暴露含糊的 refresh 字段。
2. 开发环境为兼容测试默认开放 legacy；生产环境要求显式配置两个兼容开关，任何缺省都拒绝启动。AUTH-01A 与旧前端部署时二者必须显式为 `1`，并配置 aware UTC、未来且不超过 90 天的 `AUTH_LEGACY_TOKEN_ACCEPT_UNTIL`；AUTH-01B 覆盖后在同一维护窗口显式改为 `0`。所有认证 TTL、last-seen interval 与最大窗口只接受正十进制整数，开关只接受 `0/1`，非法值在启动期失败。legacy 关闭或运行时截止后，登录响应不返回看似可用但必然被拒绝的顶层 legacy 字段。
3. REST/WS 在兼容期共用解析器。WebSocket 优先 Authorization header；query fallback 只有在 bounded legacy 窗口内才能启用，并在同一截止时间运行时自动失效。
4. AUTH-01B 负责前端改读 `session.access_token`、安全保存 `session.refresh_token`、401 单飞刷新、重试边界和 logout 接入。A 阶段不移除 query fallback，也不要求旧客户端立即刷新。
5. refresh 会立刻替换当前 access 摘要，因此使用旧 opaque access 的既有 WebSocket 会在下一事件或推送前收到 4401；AUTH-01B 必须用 successor access 重新连接。
6. AUTH-01B 覆盖部署后进入清理步骤（AUTH-01C）：关闭 WS query Token，移除登录顶层 legacy `access_token/token`，并决定将 opaque 字段提升到顶层或继续使用 `session` 契约。

旧签名 Token 没有服务端会话，无法被逐个撤销。用旧 Token 调用会话管理接口会被拒绝并提示重新登录；这是迁移期的已知边界。

## API

- `POST /django/api/v1/user/session/refresh`：使用 refresh Token 原子轮换两种凭据。
- `POST /django/api/v1/user/session/logout`：撤销当前 opaque 会话。
- `GET /django/api/v1/user/sessions`：仅列出当前用户的设备会话，不返回任何摘要。
- `POST /django/api/v1/user/sessions/{id}/revoke`：撤销当前用户拥有的指定会话。
- `POST /django/api/v1/user/sessions/revoke-others`：保留当前会话并撤销其他会话。

## 官方依据

- DRF Custom authentication：自定义认证器继承 `BaseAuthentication`，成功返回 `(user, auth)`，不尝试认证时返回 `None`，失败时抛出 `AuthenticationFailed`：<https://www.django-rest-framework.org/api-guide/authentication/#custom-authentication>
- Python `secrets`：该模块用于生成适合管理密码、账户认证与安全 Token 的强随机数；`token_urlsafe` 返回 URL-safe 随机文本：<https://docs.python.org/3/library/secrets.html>
- Django transactions：`atomic()` 提供提交/回滚边界，数据库事务用于保证一组更新的原子性：<https://docs.djangoproject.com/en/5.2/topics/db/transactions/>
- Django constraints：`UniqueConstraint`/唯一字段在数据库层保证约束，适合确定性 Token 摘要唯一性：<https://docs.djangoproject.com/en/5.2/ref/models/constraints/>
- SimpleJWT blacklist app（被比较方案）：outstanding/blacklisted token 及 refresh/sliding Token 黑名单机制：<https://django-rest-framework-simplejwt.readthedocs.io/en/stable/blacklist_app.html>

## 后果

认证请求现在会查询会话表，但获得即时撤销与统一身份语义。后续需要增加过期会话清理任务、AUTH-01B 客户端刷新，以及在迁移截止后删除 legacy 路径；这些不属于 AUTH-01A 的代码范围。
